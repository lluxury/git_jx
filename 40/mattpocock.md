倒推“古法”：从现有代码逆向出 HLD/LLD 与行为规格

ArchitectLens 是最直接匹配“HLD/LLD”需求的工具。指向一个代码库 ZIP，可以生成 SRS、BRD、HLD、LLD 的文档集，支持 CLI 和 MCP Server，可接 Claude、OpenAI、Gemini 或本地 Ollama。

性能与核心算法：把“复杂度纪律”嵌入流程，而不是事后审查
你提到的“因为性能的问题要看看核心算法是否有问题”，在传统工程里往往是最容易被流程忽略的一环——文档和测试都过了，O(n²) 才上线。目前有专门的 Skill 在设计上解决这个问题：

lemmaly 的核心规则是“算法先行”：在写任何循环、查询、递归之前，必须声明 Big-O、数据结构、算法族。它明确针对的场景包括“AI 生成的代码看起来符合习惯，但可能藏着 O(n²) 或 N+1”。它还带有一个算法纪律套件（mathguard、invariant-guard、complexity-cuts），分别处理大规模数据、不变量契约和已有代码的复杂度削减。把它放在 codeRDD 的 DEV 阶段或 SpecCrew 的 Dev 阶段作为强制子 Skill，就能把复杂度审视从“事后性能测试”前移到“设计/编码决策点”。

Performance Oracle 覆盖六个维度：算法复杂度、数据库查询、内存管理、缓存策略、网络传输、前端渲染。它的特色是规模投影——不只判断当前复杂度，还要求投影 10x、100x、1000x 数据量下的表现，并标记任何“无正当理由的 O(n²) 及以上”模式。如果你的“核心算法”涉及数据量增长后的可扩展性，这个框架比单纯的 Big-O 标注更实战。

complexity-cuts 则是 corrective playbook，专门处理“已经上线、已经慢了的代码”：嵌套循环、N+1、重复计算等。如果倒推阶段发现核心模块已经有性能问题，可以用它来做针对性重构，而不是从设计层重新推一遍。

🏗️ 先科普：传统软件工程流程的骨架
一套经典的“古法”流程，核心是分阶段推进，每个阶段有明确的输入、输出和负责人，上一个阶段的产物是下一个阶段的“合同”。

1. 需求分析
产出 SRS（软件需求规格说明书） 。由 PM/业务分析师 负责，把“要解决什么问题”固化成可验证的条目。

2. 概要设计（HLD）
产出架构图、模块划分、接口定义、数据库设计。由架构师主导，解决“系统由哪些大的部分组成，它们怎么连接”。HLD 不涉及具体代码怎么写。

3. 详细设计（LLD）
产出类图、时序图、函数签名、单元测试计划。由高级开发/设计师负责，把 HLD 的每个模块拆解到“开发拿到就能直接编码”的程度。

4. 编码与单元测试
开发按 LLD 实现。传统流程的关键在于：代码是对 LLD 的翻译，而不是即兴创作。

5. 集成测试 & 系统测试
QA 按 SRS 和 HLD 验证功能与集成，性能测试也常在此阶段介入。

6. 部署与维护
上线、监控、修复。性能问题往往在这里才暴露——这正是你想用 AI 提前拦截的痛点。

传统流程的纪律性体现在：没有 HLD 不进入 LLD，没有 LLD 不进入编码。AI 工具要复现的，就是这种“阶段门禁”的感觉。

① 概要设计（HLD）—— 一页纸版本

不需要完整的6章模板。只写四块：

关键约束：性能目标、数据量级、部署形态（单机/云、有没有外网）。有就写，没有就写“无特殊约束”。

这一页的作用是让客户和老员工一眼看出系统边界和风险点在哪里，而不是证明设计有多细。

② 关键决策记录（ADR-lite）—— 一条一行

老牌客户最在意的是“为什么当时这么定”，而不是设计图画得多漂亮。代码里看不出“为什么金额用分不用小数”“为什么和甲方用文件对账而不是实时接口”。

每条决策只记四个字段：决策 → 理由 → 被否掉的备选 → 影响范围。比如：

“支付失败走人工补账，不走自动冲正。理由：对账口径甲方只认人工确认。备选：自动冲正（被否，对账对不上）。影响：运营需要一条后台补账入口。”

有了这一张表，后面无论谁接手、客户怎么问，都能一句话回答“当时为什么”。 这比补十页详细设计都管用。

③ 交接快照（Runbook 一页纸）

AI生成的代码如果“只有代码没有上下文”，换一个人就会变成黑盒子。补一页系统怎么跑起来：部署在哪、数据存哪、谁能登入、出事看哪里。这四样写清楚，客户方运维或你们后续接手的人不至于从零考古。如果系统还没有正式部署，这一页可以先用“本地怎么启动 + 依赖哪些外部服务”代替。

👤 只设三个“可执行”的岗位
不需要还原 PM、架构师、开发、QA 一整套。每个岗位只写“对什么结果负责”和“不负责什么”，边界指向具体的文档或决策，不写笼统的能力描述。

业务负责人（可以是你或对接客户的人）

负责：需求清单的“现行有效”版本；确认哪些需求本期做、哪些不做；在HLD上签字认可系统边界。

不负责：技术选型的正确性、代码质量。

技术负责人（可以是你或资深开发）

负责：HLD的一页纸；关键决策记录每一条都有人拍板；核心算法或关键路径的复杂度有交代（哪怕只是一句“这个查询走索引，数据量到百万级需要换方案”）。

不负责：每个函数的实现细节、测试用例的数量。

交付负责人（可以是PM或你自己兼）

负责：交接快照保持最新；客户拿到的文档版本和实际运行的系统对得上；变更时顺手更新对应那一页。

不负责：设计是否正确、代码有没有bug。

三个岗位可以一人多角，但每份文档必须有且只有一个最终责任人。老牌客户验收时问“这份设计谁确认的”，你能指到具体的人，比十页流程说明更有说服力。

🧩 AI跳步后的“反向补法”
AI已经跳到代码或自己生成了文档，不需要推倒重来。用代码反推 + 确认的方式，半天到一天就能把上面三份补到“可用”状态：

从现有代码扫出HLD的四块：用AI或你自己，让工具读一遍代码库，只回答“系统由哪些模块组成、数据从哪进从哪出、对外接口有哪些”。你只确认和修正，不要求它生成完整设计文档。这是AI反向补文档最务实的方式——代码已经存在，它比人的记忆更接近事实。

把AI生成的零散文档合并、裁剪：AI跳步时往往会吐出多个命名各异的md文件。不要试图整理成一套“体系”。只保留三类内容：架构边界（并入HLD一页纸）、决策理由（逐条抽进ADR-lite）、运行方式（并入交接快照）。其余重复的、过期的、没人会看的，直接归档不引用。

🧬 第一层：代码静态分析——看“设计上有没有埋雷”
这一层解决“算法设计”和“数据流/业务逻辑”的总结问题，不需要等 Trace 数据，直接读代码。

算法设计审查：evaluate 或 review-perf

evaluate 的定位很精准：在部署新微服务之前，主动识别核心处理逻辑和数据库交互中的潜在瓶颈。它会评估关键代码段的时间/空间复杂度、数据结构是否适合当前规模，以及架构是否支持水平扩展。这正是你担心的“核心算法是否有问题”的直接对应物。

review-perf 覆盖面更宽：数据库查询（N+1、索引缺失）+ 算法复杂度 + 前端瓶颈 + 资源泄漏四路并行扫描，每条发现都要求追溯到具体的文件和行号，并且强制区分“热路径”和“冷路径”——一个 O(n²) 在初始化代码里可能可以接受，但在每次请求都走的热路径上就是事故。

数据流与业务逻辑：codebase-analyzer

它的方法是 SCOPE → ROUTE → EFFECT → BREAK → SHIP，专门追踪调用链、数据流、运行时接线和模块职责，每一条结论都要求锚定到 path:symbol:line。这比泛泛的“架构图”更贴近你要的“数据流 + 业务逻辑”总结，因为它是从代码事实出发的，而不是让 AI 凭印象画图。

如果你想要更“架构级”的通读，前面提到的“AI 架构审查员”Skill 也可以参考：它扫描整个微服务项目，提取服务依赖、API 数量、数据库归属，再让模型做多维审查，产出一张带评分的“架构体检报告”。但它偏重“项目全貌评估”，不是专门为性能算法分析设计的，可以作为辅助而非主力。

🔗 第二层：链路追踪分析——看“实际哪里慢、为什么慢”
静态分析告诉你“可能有问题”，链路追踪告诉你“问题确实发生了，发生在哪一跳，是执行慢、等待慢、还是重试拖慢的”。

核心 Skill：distributed-trace-analysis

这个 Skill 的设计直接回应了你“不要看时间线、要还原因果路径”的需求。它的核心判断是：最长 Span 不一定是根因。它会区分排队等待、重试、下游等待和执行耗时，把 Trace、指标和日志放进同一时间窗口做交叉验证，避免“看到最长 Span 就直接归责”的误判。对于微服务性能问题，等待型延迟（下游慢、连接池排队、重试风暴）往往比本地计算更常见，而这个 Skill 正是为区分这两类延迟设计的。

配套工具：mcp-server-jaeger

如果你已经有 Jaeger 数据，这个 MCP Server 让 AI 助手能渐进式地查询 Trace，而不是一次性塞入几 MB 的原始数据。它先做服务发现，再看 Trace 概览，然后定向隔离最慢的 Span 或错误 Span，最后深挖细节。这样可以避免上下文窗口爆炸，也减少了 AI 在无关 Span 上浪费注意力。把它和 distributed-trace-analysis 搭配，前者负责“取数据”，后者负责“读故事、找因果”。

② 为了“避免 JOIN”预计算宽表，每次变更全量刷新

把评价关系、权重、得分展开成一张宽表，查询确实快了。但写路径变成“先删后插整张宽表”或“全量 UPDATE”。单次写入看起来不慢，但每次提交都重刷全量，总计算量随人数线性甚至超线性增长。

识别信号：SDD 的 [Confirmed] 数据模型里，如果存在一张“汇总宽表”或“物化视图”，且它的刷新逻辑是 DELETE + INSERT 或全量 UPDATE，而不是按主键增量 UPSERT，基本可以确认。

③ 为了“加速排名”物化排名表，每次提交全量重排

排名查询慢，于是把排名物化成一张表。但每次有人提交评分，触发的是“重新加载所有人得分 → 全量排序 → 回写排名”。O(N log N) 的写路径，人数一上去就是灾难。

识别信号：写路径的调用链里出现“load all scores”或“select * from scores where period=?”然后内存排序再批量写回。SDD 的 [Inferred] 调用链能看到这个模式。

④ 循环内查询伪装成“分批优化”

代码看起来是分批处理（每批 100 条），但每批内部又对全量数据做了一次聚合或校验。开发以为“分批 = 优化”，实际总计算量没变，甚至因为重复加载而更大。

⑤ 为了“减少数据库压力”把计算推到应用层，结果每次请求全量加载

识别信号：SDD 的调用链里，写路径或查询路径出现“findAll / select * 不带过滤条件”然后内存过滤/聚合。这是“局部优化”最隐蔽的一种，因为数据库监控看起来正常，但应用层资源暴涨。
